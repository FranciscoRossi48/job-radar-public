# job-radar — convenciones

Pipeline local para buscar y filtrar avisos de Data/BI en CH, NL y LU. Desde el 27/10/2026 solo CH está activo (`searches.yaml: active_countries`); NL y LU quedan configurados pero en pausa. La especificación vigente está en `SPEC.md`.

## Comandos
- `uv run pytest` — tests (sin red; los adapters reciben funciones inyectadas o respuestas grabadas)
- `JOB_RADAR_LIVE=1 [JOB_RADAR_MODEL=gemini-3.5-flash-lite] uv run pytest -m live -s` — valida el rubric con Gemini real sobre `tests/fixtures/jobs/cases.json` (gasta ~10 requests)
- `uv run job-radar run-daily [--eval-limit N] [--skip-ingest] [--skip-evaluate]` — ingest → evaluate → export; resumen en `logs/runs.jsonl`
- `uv run job-radar evaluate [-n N]` / `rescore` / `export [--all | --day YYYY-MM-DD] [--min-score X]` / `reprefilter` / `dedup` / `backup`
- `deploy/install.sh [HORA] [MIN] [HORA_RESCATE] [MIN_RESCATE]` / `deploy/uninstall.sh` — launchd: `com.jobradar.daily` (completa) y `com.jobradar.catchup` (`--skip-ingest`, evalúa pendientes)
- `uv run job-radar mcp-config` — bloque para `claude_desktop_config.json`; el servidor es `uv run job-radar-mcp` (stdio)
- `uv run ruff check . && uv run ruff format .`
- `uv run job-radar ingest [-q QUERY] [-c CH] [-s linkedin|swissdevjobs|iamexpat|ats|greenhouse:token] [--limit N] [--companies archivo.yaml]` / `uv run job-radar stats`

## Reglas
- Nada hardcodeado: queries, países, regex, pesos, umbrales y perfil van en `config/*.yaml`, con un modelo Pydantic en `src/job_radar/config.py`. Si agregás una clave al YAML, agregala también al modelo.
- Secretos solo en `.env` (ver `.env.example`). Nunca cookies ni credenciales de LinkedIn: solo endpoints públicos.
- Cada fuente es un adapter (`ingest/base.py: Adapter`) que devuelve `RawJob`. `run_adapters` aísla las fallas: una fuente rota o con rate limit nunca corta la corrida.
- Adapters HTTP: usan `FetchContext` (`ingest/common.py`) con el cliente `http.Http` (pausa, backoff, 429 -> `RateLimited`). Fuentes N+1 (SmartRecruiters, Workday, SuccessFactors, BrassRing, SwissDevJobs, IamExpat) filtran título/país antes de pedir el detalle y no lo vuelven a pedir para ids conocidos (`db.known_ids`).
- `matador` (WordPress con Matador Jobs, usado por consultoras como RM Group) no es N+1: la API REST trae el contenido, de a 100 por página; la ubicación sale del bloque de metadatos del contenido y el id es `token:id`.
- `rss` (feed de avisos, ej. PROSTAFF): el feed trae solo un resumen; para avisos nuevos con título relevante pide el detalle y usa su JSON-LD `JobPosting` (descripción completa y ubicación), hasta `max_details_per_company`; si no consigue el detalle (falla o tope) sale con descripción vacía para que quede `no_description` y se reintente. `extra.url` y `extra.title_strip` (regex para sufijos como "(#26332) - CONTRACT").
- Los ATS solo guardan avisos de los países de `searches.yaml: geo` (`geo.CountryResolver`). Workday: detecta solo el facet de país (ids globales) y, si no hay, saltea avisos de una única ubicación fuera de CH/NL/LU antes de pedir el detalle. SuccessFactors y BrassRing (UBS) también filtran por país y título antes de bajar cada aviso. Al sumar empresas a `companies.yaml`, verificá el token con `ingest -s <ats>:<token>`; ojo con YAML: `name: On` se lee como booleano (va entre comillas).
- Perfil: `residency_countries: [CH]`; los tests fuerzan `[]` en `conftest.py`.
- Deduplicación en `db.upsert_job`: id (PK), `dedup_key` (empresa+título normalizado+país, limpiando `@ Empresa` y `(On-site/Hybrid)`) y simhash (`dedup.py`, con `simhash_same_title_max_distance` más permisivo cuando coinciden título normalizado y país para atrapar agregadores), solo contra avisos vivos dentro de la ventana.
- LinkedIn (`JobSpyAdapter`): el listado va sin descripciones y `_with_details` las pide después solo para avisos nuevos con título relevante, con `searches.jobspy.linkedin_detail_delay_s`; corta tras `linkedin_detail_max_failures` fallas seguidas (usa `_fetch_details`, interno de JobSpy). Los que quedan `no_description` se reintentan al reaparecer. Tras una búsqueda cortada por 429, la pausa siguiente (otra búsqueda o las descripciones) es `cooldown_after_cut_s`. Lo incompleto (listado cortado, o al menos `linkedin_missing_warn_min` avisos sin descripción) va a `adapter.warnings` -> `partial_sources` en el resumen -> push "CSV con problemas". Cada búsqueda queda en `sources.jobspy:linkedin.searches` (resultados, horas, `cut`); el rescate (`--skip-ingest`) las retoma con `pipeline.linkedin_retry_adapter` (offset = lo ya traído, más los `no_description` de hoy) como paso `linkedin_retry`, una vez por día (`jobspy.retry_in_rescue`). No es paso `ingest`: no cuenta para `full_run_today` ni `last_clean_ingest`.
- Toda la SQL vive en `db.py`. Columnas nuevas: agregarlas a `_MIGRATIONS`. SQLite en modo WAL. El lease (`claimed_at/claimed_by`) es independiente de `status`.
- El scoring es determinístico y vive en Python (`scoring.py`). El LLM solo extrae features (`models.EvaluationFeatures`, compartido por Gemini y Claude). Cada evaluación guarda `score_breakdown`.
- Gemini: API en plan pago prepago (desde 16/10/2026; la suscripción AI Pro no cubre la API). `config/llm.yaml` define una cadena de modelos (3.8-flash primero, Lite de respaldo). 402 = sin saldo -> `BillingExhausted`, corta la corrida. `llm_calls` guarda tokens; `job-radar usage` los resume. Cuota diaria agotada o 5xx persistente -> siguiente modelo; el último disponible recibe `last_model_retries`. Cada request tiene `request_timeout_s` (sin timeout, un pedido en vuelo cuando la Mac se duerme colgaba la corrida para siempre). Validá un modelo nuevo con el test live antes de sumarlo (`gemini-3.5-flash` es alias de 3.6). `llm_calls` registra cada request para el RPD local. gemini-2.5-flash ya no está disponible para cuentas nuevas.
- MCP (`mcp_server.py`): SDK `mcp` 2.x, donde FastMCP se llama `MCPServer`. La lógica vive en funciones `tool_*(cfg, conn, ...)` testeables sin protocolo; el servidor solo las envuelve. Nunca escribir a stdout en el servidor (es el canal del protocolo). `save_evaluations` valida ítem por ítem y no aborta el lote.
- Logging: `logs.setup_logging(cfg)` en cada comando del CLI (consola + `logs/job-radar.log` en JSON con rotación). Usar `extra={...}` para campos estructurados. `daily.run_daily` aísla cada paso: un paso roto no corta los siguientes, y el ingest cuenta los ERROR de red del log (`NetworkErrorCounter`, `network_errors`; JobSpy no lanza excepción). Con `--once-per-day` (launchd cada 30 min) espera DNS (`app.network`) y `logs.daily_run_done` repite el día si hubo errores de red, hasta `max_daily_attempts`. Al final manda un push de ntfy (`daily.ntfy_message`/`send_ntfy`, tema en `.env: NTFY_TOPIC`, `app.ntfy`; `conftest.py` lo apaga), que en el rescate (`--skip-ingest`) avisa si hoy no hubo corrida completa (`logs.full_run_today`). launchd no lanza la corrida diaria en despertares oscuros, pero sí el horario fijo del rescate. Además, si `app.notify_on_error` es True dispara una notificación nativa de macOS (`osascript`) ante pasos fallidos o corte de evaluación (`conftest.py` lo apaga en tests).
- Respaldo: `backup.backup_db` (paso de `run-daily`, o `job-radar backup`) deja `jobs_FECHA.db.gz` en `<carpeta espejo>/<app.backup.subdir>` y rota a `keep` días. Sin carpeta espejo lanza error para que se vea como paso fallido. `conftest.py` lo apaga.
- Países en pausa: `active_countries` (`searches.active_codes`) también filtra la evaluación de Gemini, `get_batch`, `get_shortlist`, el push y los CSV diario y `--day` (`countries` en `db.pending_for_evaluation`/`current_evaluations`/`claim_*`); el CSV `--all` conserva el histórico.
- Export: cada CSV se copia a `app.exports_mirror_dirs` (Google Drive para escritorio; acepta ~ y comodines). Los tests fuerzan esa lista vacía en `conftest.py`: nunca escribir en el Drive real desde tests.
- Decisiones (`jobs.decision`: applied | discarded): los jobs decididos se excluyen de `get_batch`, `get_shortlist` y del CSV diario (`include_decided=True` para verlos; `export --all` los muestra con su decisión).
- Export: el modo por defecto ("novedades") solo incluye jobs con `exported_at` NULL y los marca; `--all` y `--day` no marcan. Los `duplicate` nunca salen en reportes.
- Búsquedas: `searches.queries` corren siempre y `rotating_queries` por turnos (`queries_for(día)`, `rotating_per_day`); `-q` desactiva la rotación y la ventana corta. El total diario queda en 3 por el 429 de LinkedIn. Las fijas usan `hours_old` = horas desde la última corrida limpia de esa fuente (`logs.last_clean_ingest`: sin error, sin errores de red, sin búsquedas cortadas) + margen, entre `since_last_run_min_h` y `hours_old` (`jobspy_adapter.window_hours`); las rotativas, `hours_old`.
- Roles vecinos: títulos que pasan `include_any` sin nombrar datos (AI/ML, analistas, arquitectos, SQL/database; backend/Python puro no entra) usan `scoring.bonus.adjacent_role` (regex sobre el título): exigen `min_stack` tecnologías del perfil o cuentan como `other`. `reprefilter` reabre los `title_not_relevant` vistos dentro de `stale_days`; correr `dedup` después.
- Idiomas a favor (`scoring.bonus.lang`, hoy `es`): si el aviso los pide suman por nivel (required/nice) y nunca penalizan. Desde el rubric v2 el LLM marca el español como `es` (antes caía en `other` y excluía).
- Stack: el bonus usa la unión de `stack_match` del LLM y `scoring.stack_in_text` (regex sobre título+descripción con `profile.stack_aliases`), siempre limitado al stack del perfil. Así un `rescore` refleja cambios del stack sin reevaluar.
- Si un LLM ignora una instrucción del rubric de forma sistemática, corregilo en `scoring.py` (determinístico) en vez de agrandar el prompt (ej. `red_flag_ignore`).
- El rubric se versiona (`prompts/rubric_vN.md`); si cambia la semántica, creá una versión nueva.
- Tests: casos borde de regex como tests parametrizados; los tests leen los YAML reales de `config/`. Adapters HTTP con `respx` y fixtures en `tests/fixtures/http/`.
- Código y comentarios en español rioplatense; identificadores en inglés.
